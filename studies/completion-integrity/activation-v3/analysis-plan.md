# Completion Integrity activation v3 — prospective analysis plan

## Question

After repairing the owner-generated identity and version-routing defects exposed
by activation v2 and its first fresh qualification receipt, can the complete
versioned owner wrapper activate on two new sacrificial Codex task roots without
crossing the reporter capability boundary? If it can, are B0 and T1 terminal
claims structurally valid and accurate on both roots?

This remains activation calibration, not a population-effect study. Two task
roots cannot estimate reliability, transfer, model quality, or downstream
benefit.

## Prospective revision boundary

Activation v2 remains `protocol_invalid / revise_activation_adapter`. Its tasks,
answers, raw root, freeze, and terminal decision are historical and are not
retried or reinterpreted.

V3 uses:

- two genuinely new Python/TypeScript repository graphs;
- a new private pack, qualification lineage, raw root, study identity, and
  preregistration;
- activation IDs, qualification IDs, truth IDs, submission IDs, and schedule
  cells derived from the exact v3 study/private-pack identity;
- a no-call full-wrapper qualification over all six scheduled identities;
- a new prospective Study Quality Profile;
- fresh provider schema and reporter-boundary probes;
- the same one-submit/no-resume stop rule.

The first fresh-root deterministic qualification exposed an owner-tool defect:
its generated receipt still named `activation-v1`. That receipt is retained as
invalid and contributes no passing v3 evidence. The version-derived tool repair
was committed before the second full qualification, which must pass on all 16
challenge cases and both evaluator repeats per case.

## Frozen schedule

The schedule is derived from the two qualification receipt task IDs and is
fixed sequentially: executor, B0 reporter, and T1 reporter for the Python root,
then the same sequence for the TypeScript root. Every cell is submitted once at
most. A submitted or ambiguous attempt is never retried or resumed.

The executor receives one private task fixture and an ephemeral writable
workspace. The deterministic evaluator runs only after the executor stops and
is never mounted into the executor or reporter.

B0 and T1 receive the same sealed evidence tree for a task. They receive no
task artifact, evaluator, oracle, executor workspace, solution, mutant, or
intervention mount. The reporter boundary is outer read-only Docker isolation;
it is evidence-only and non-mutating, not tool-free.

## Conditions

- `B0`: minimal schema-bound terminal report from sealed owner evidence;
- `T1`: the same evidence/schema plus explicit non-compensating requirement
  reconciliation.

The B0/T1 comparison changes only the reporter prompt. Model, reasoning effort,
evidence bytes, schema, image, budget, and capability boundary remain matched.

## Outcomes and decision

For each root, retain:

1. executor terminal validity;
2. complete observable-chain state;
3. executor claim agreement with deterministic truth and observed commands;
4. B0/T1 structural validity and agreement with frozen truth;
5. unchanged evidence identity and zero forbidden mounts;
6. exact tool, cost, latency, credential-scan, and failure observations.

The adapter becomes eligible only when all six cells are valid, both executor
chains are complete, every reporter sees/leaves the same evidence hash, no
forbidden mount or credential persistence occurs, T1 agrees on both roots, and
T1 is not descriptively worse than B0.

Otherwise retain the exact terminal disposition:

- protocol/capability failure → revise adapter;
- incomplete chain → revise capture mapping;
- T1 worse than B0 → reject exact T1 prompt;
- valid protocol with a T1 claim error → revise reporter protocol;
- all gates pass → qualify only this versioned adapter for future task-supply
  development.

No result from activation v3 admits the larger 16-root study. That study still
requires independent task roots, pilot-informed sizing, screening/confirmation
roles, and a separately frozen action rule.

## Stop rules

Stop before the first scheduled call if any public file, private pack,
qualification receipt, assessment, full-wrapper receipt, quality profile,
preflight, image identity, capability probe, schema probe, code hash, prompt,
schedule, budget, or owner rule differs from the freeze.

After submission, stop the remaining schedule on ambiguity, timeout without a
terminal record, credential persistence, evidence mutation, forbidden mount,
evaluator operational failure, output-limit breach, or any other protocol
integrity failure. Preserve prior/partial evidence and do not retry.
